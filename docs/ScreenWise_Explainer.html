1. Big picture — how the pieces connect

ScreenWise takes a CSV of 400 people's screen-time and lifestyle habits, turns it into a classifier that predicts a wellness category (Low / Moderate / High), and serves that classifier over HTTP. There are four layers, and each one only talks to the next through files or JSON:

data/ScreenTime vs MentalWellness.csv (400 rows, 15 real columns) │ ▼ ml/preprocess.py → load · clean · engineer features · build target labels │ ▼ ml/features.py → ColumnTransformer (scale numbers, one-hot encode categories) │ ▼ ml/train.py → train/test split · 5-fold CV · GridSearchCV · pick best · evaluate │ (uses ml/evaluate.py for metrics) ▼ artifacts/ → model.pkl, preprocessor.pkl, metrics.json, feature_info.json, model_metadata.json │ ▼ ml/predict.py → WellnessPredictor: loads artifacts, predicts for one person │ ▼ backend/app/ → FastAPI: /health · /model-info · /predict (JSON over HTTP)
The key idea: training and serving are deliberately separated. ml/train.py writes everything it learned into artifacts/. The backend never trains anything — it just loads those artifacts and calls them. That is why you must run python -m ml.train before the backend has a model.

2. Part 1 — notebooks/EDA.ipynb: why and what

2.1 Why do EDA at all?

EDA (Exploratory Data Analysis) is the "look before you build" step. Before writing any model you need to answer questions the code cannot guess for you:

  • Is the data clean? Missing values, duplicates, junk columns, impossible values (a 40-hour screen day?).
  • What does each column actually contain? Ranges, skew, category counts — so validation rules later are realistic, not invented.
  • Which relationships exist? Correlations tell you which features are plausible predictors and warn you about redundancy.
  • Is the target usable as-is? This is the single most important question in this project — see section 2.4. It is what stops the model from "cheating".

The notebook's own header says it plainly: it inspects the raw data and documents cleaning decisions. It deliberately does not build the deployed model — that job belongs to ml/train.py. So the notebook is a justification document for the choices the pipeline then makes in code.

2.3 The junk column and the id column (cleaning decisions)

Unnamed: 15

An artefact of a trailing comma in the CSV header. It is entirely empty, not part of the real schema. Both the notebook and preprocess.load_raw_data() drop any column whose name starts with Unnamed.

user_id

A unique identifier (U0001…U0400). It carries no signal about wellness and could let a model memorise rows, so clean_data() drops it.

2.4 Section 7 explained — the most important finding

The project brief suggested a wellness score built from three self-reported indicators: productivity, sleep quality, and (inverted) stress. The notebook tests that hypothesis instead of assuming it:

norm_prod   = productivity_0_100 / 100
norm_sleepq = (sleep_quality_1_5 - 1) / (max - 1)
inv_stress  = (10 - stress_level_0_10) / 10

combo        = norm_prod + norm_sleepq + inv_stress
combo_scaled = rescale combo to 0–100

corr(combo_scaled, mental_wellness_index_0_100) ≈ 0.9572

A 0.96 correlation means the shipped mental_wellness_index_0_100 column is essentially that formula already applied. Two consequences follow, and both are implemented in ml/preprocess.py:

  1. Reuse the column instead of re-deriving it. The exact index is better than any approximation we could rebuild, so it becomes the target directly.
  2. Exclude its ingredients from the inputs — data leakage prevention. productivity_0_100, sleep_quality_1_5 and stress_level_0_10 are listed in LEAKAGE_COLUMNS and never used as model features. If they were, the model could "predict" the target by basically re-reading it — impressive accuracy, zero real value.
Why 0.96 and not 1.00? The index is heavily skewed and the reconstruction is an approximation (different rounding/scale choices). A very strong but non-perfect match is exactly what you expect if the column was derived from those indicators. Either way the conclusion — reuse the column, exclude the ingredients — is the safe one.

2.5 Section 8 explained — why quantile buckets, not fixed ranges

A naive split of 0–100 into thirds (Low 0–33, Moderate 34–66, High 67–100) would fail here because the index is right-skewed: mean ≈ 20 and 75th percentile ≈ 31, so over 70% of rows would land in "Low" and "High" would be almost empty. A classifier trained on that is useless — it could score well by mostly predicting one class.

Instead the notebook uses pd.qcut(..., q=3) — terciles, i.e. cut at the 33rd and 66th percentiles computed on the actual data. That yields balanced classes and, as a bonus, the exact bin edges are needed later to turn a class back into a 0–100 score.

EDA output that the ML code literally consumes:
  • The leakage column list → LEAKAGE_COLUMNS in preprocess.py.
  • The tercile bin edges [0.0, 6.6, 25.1, 97.0] → saved to feature_info.json → used in predict.py to compute the score.
  • Observed value ranges → the numeric limits in backend/app/schemas.py.
  • The three class names Low/Moderate/High → the labels everywhere.

3. Part 2 — The ML pipeline

Five files, each with one job. Flow order: preprocess → features → train → evaluate, then predict at serving time.

preprocess.py ──► features.py ──► train.py ──► evaluate.py │ │ └─ data prep, target labels └─ metrics (accuracy, P/R/F1, confusion matrix) │ ▼ artifacts/*.pkl, *.json │ ▼ predict.py (inference)

3.1 ml/preprocess.py — getting the data ready

This file defines the "contract" of the dataset: which columns are features, which are leakage, and how the target is built.

Constants (the contract)

  • NUMERIC_FEATURES = age, screen_time_hours, work_screen_hours, leisure_screen_hours, sleep_hours, exercise_minutes_per_week, social_hours_per_week, leisure_screen_ratio (8, the last one derived).
  • CATEGORICAL_FEATURES = gender, occupation, work_mode (3).
  • ALL_FEATURES = 11 total inputs.
  • LEAKAGE_COLUMNS = productivity_0_100, sleep_quality_1_5, stress_level_0_10 — present in the CSV, excluded from inputs.

Functions

FunctionWhat it does
load_raw_data()Reads the CSV and drops Unnamed* columns.
clean_data()Drops duplicates and user_id, then applies strict range filters (age 10–100, screen/sleep hours 0–24, sleep quality 1–5, stress 0–10, productivity 0–100, non-negative exercise/social, index 0–100). Any out-of-range row is removed, not repaired. Resets the index.
engineer_features()Adds one derived column: leisure_screen_ratio = leisure_screen_hours / screen_time_hours (0-division guarded with replace(0, NaN) then fillna(0)). It deliberately uses only non-leakage inputs.
construct_target()Uses mental_wellness_index_0_100 as the score and calls pd.qcut(q=3, labels=["Low","Moderate","High"]) to create the wellness_category target. Returns the dataframe plus the bin edges so they can be saved and reused at inference.
load_and_prepare()The one-line pipeline: load → clean → engineer → construct target. Returns (df, bin_edges).
The lengthy docstring in construct_target() is effectively a pointer back to EDA section 7 and 8 — it records why the existing column is reused, why the three indicators are excluded, and why fixed 0–33/34–66/67–100 thresholds were rejected in favour of terciles.

3.2 ml/features.py — turning inputs into model-ready numbers

A ColumnTransformer with two pipelines:

  • Numeric (8 columns) → StandardScaler (mean 0, std 1). Scaling matters a lot here because the model that won is a linear one — exercise_minutes_per_week (up to 372) would otherwise dwarf leisure_screen_ratio (0–1).
  • Categorical (3 columns) → OneHotEncoder(handle_unknown="ignore"), producing one 0/1 column per category (3 + 5 + 3 = 11 columns).

Result: 8 scaled numbers + 11 one-hot flags = 19 model input columns. This exact list is saved as output_feature_names in feature_info.json. The preprocessor is fit on the training split only, so scaling statistics never leak from the test set.

3.3 ml/train.py — comparing, tuning, choosing, saving

Step 1 — split

train_test_split(test_size=0.2, random_state=42, stratify=y): 320 rows train / 80 rows test, with the class balance preserved in both (stratify).

Step 2 — preprocess

build_preprocessor() is fitted on X_train, then applied to both splits with transform. Vocabulary/scale come only from training data.

Step 3 — cross-validated comparison of four candidates

StratifiedKFold(n_splits=5) on the training set, scored by accuracy:

ModelCV accuracy (mean)Std
LogisticRegression0.64690.0470
RandomForest0.63130.0590
GradientBoosting0.61250.0695
DecisionTree0.54690.0797

Step 4 — hyperparameter tuning

GridSearchCV (5-fold, accuracy, n_jobs=-1) is run for:

  • RandomForest over n_estimators [100,200,300], max_depth [None,5,10], min_samples_split [2,5], min_samples_leaf [1,2] → best = defaults at n_estimators=100, max_depth=None, min_samples_split=2, min_samples_leaf=1, CV 0.6313.
  • GradientBoosting over n_estimators [100,200], max_depth [2,3,4], learning_rate [0.05,0.1] → best = n_estimators=100, max_depth=3, learning_rate=0.05, CV 0.6250.

Tuning did not beat the untuned Logistic Regression — an honest, useful finding on a small dataset.

Step 5 — automatic selection

The script builds a candidate set of {tuned RandomForest, tuned GradientBoosting, untuned LogisticRegression, untuned DecisionTree} and picks the one with the highest CV accuracy with max(candidates, key=...). Winner: LogisticRegression (0.6469).

Why a "Logistic" model and not a "Linear" one? Logistic Regression is a linear classifier, not linear regression. Linear regression predicts a continuous number; Logistic Regression predicts the probability of class membership (via the sigmoid function) and is trained for classification. Our target is a category (Low/Moderate/High), so a classifier is the correct family. Under the hood it is still a linear model in the scaled feature space, which is why it is simple, fast, and has low variance — and why it survived on 400 noisy rows. It is also multinomial here (three classes), and with predict_proba it gives the confidence shown in the UI.

Step 6 — final fit and one-time test evaluation

The winner is refit on all 320 training rows, then evaluated once on the held-out 80 test rows (never used for selection):

MetricTrainTest (final)
Accuracy0.6910.600
Precision (weighted)0.6830.594
Recall (weighted)0.6910.600
F1 (weighted)0.6840.596

Train > test is the expected small gap on a 400-row dataset. The confusion matrix (rows = actual, columns = predicted, labels [High, Low, Moderate]) on test:

[ [20,  2,  5],     # High: 20 correct, 2 → Low, 5 → Moderate
  [ 3, 17,  7],     # Low:  17 correct, 3 → High, 7 → Moderate
  [ 5, 10, 11] ]    # Moderate: 11 correct, 5 → High, 10 → Low

Read it plainly: "High" and "Low" are detected reasonably; "Moderate" is the hard one (only 11 of 26 correct), which is typical when the middle class is genuinely a fuzzy boundary.

Step 7 — feature importance (explainability)

Tree models expose feature_importances_. Logistic Regression does not, so the code falls back to the mean absolute standardised coefficient across the three classes, normalised to sum to 1:

raw = np.abs(best_model.coef_).mean(axis=0)
importances = raw / raw.sum()

This is what powers the "top factors" bars in the result screen. Feature names are cleaned by stripping the num__ / cat__ prefixes added by the ColumnTransformer.

3.4 ml/evaluate.py — shared metrics

A single helper, evaluate_predictions(y_true, y_pred), returning accuracy, weighted precision/recall/F1, the confusion matrix (plus its label order), and a full classification_report as a dict. It is used by train.py for the train and test evaluations and by the test suite, so metrics are computed the same way everywhere.

3.5 ml/predict.py — the serving wrapper

WellnessPredictor loads the four artifacts (model, preprocessor, feature_info, metadata) once, then for a single record:

  1. Builds a one-row DataFrame and recomputes the derived feature leisure_screen_ratio (inference must repeat training-time feature engineering).
  2. Orders columns exactly as numeric_features + categorical_features from feature_info.json (column order matters).
  3. Runs preprocessor.transform then model.predict.
  4. If the model supports predict_proba, takes the probability of the predicted class as confidence.
  5. Converts the class back to a 0–100 score using the saved tercile bin edges, taking the midpoint of the predicted band: 
    Low      → (0.0 + 6.6)  / 2 =  3.3
Moderate → (6.6 + 25.1) / 2 = 15.85
High     → (25.1 + 97.0)/ 2 = 61.05
  6. Attaches the top 5 stored factors for explainability.

Returns {prediction, score, confidence, top_factors}.

A module-level get_predictor() caches a singleton so artifacts are read from disk only once per process.

Minor observation (not a bug report, and not changed): the leisure_screen_ratio guard differs slightly between the two files — training divides by NaN-then-zero-fills when total screen time is 0, while inference divides by 1. It only matters for a zero-screen-time row, which the real dataset never contains, so predictions are unaffected in practice. Likewise the README says the ratio is "clipped to [0,1]"; the code does not actually clip it.

4. Part 3 — The backend (FastAPI)

Four small files in backend/app/. There is no ML logic here at all — the backend is a thin, validated HTTP shell around ml/predict.py.

4.1 config.py — the only configuration

  • Resolves BACKEND_DIR, PROJECT_ROOT and ARTIFACTS_DIR by path arithmetic, so no hard-coded absolute paths.
  • ALLOWED_ORIGINS = the two local Vite dev URLs (localhost:5173 and 127.0.0.1:5173) for CORS.
  • API_TITLE = "ScreenWise API", API_VERSION = "1.0.0".

4.2 schemas.py — the request/response contract

Pydantic models. This is where input validation lives, and it is why bad requests never reach the model.

PredictionRequest — 10 fields

Note there is no leisure_screen_ratio field — the client never sends it; predict.py derives it internally. The allowed categories are exactly the ones recorded in feature_info.json, and an example payload is embedded for the auto-generated Swagger docs.

Other models

  • TopFactor — {feature, importance}.
  • PredictionResponse — {prediction: Low|Moderate|High, score: float, confidence: float|None, top_factors: list[TopFactor]}.
  • HealthResponse — {status, model_loaded}.
  • ModelInfoResponse — mirror of model_metadata.json: model_name, training_date, dataset, random_state, features, metrics, target_construction.

4.3 predictor.py — the bridge to the ML layer

Because the backend lives in a subfolder, it must be able to import the ml package from the project root:

if str(PROJECT_ROOT) not in sys.path:
    sys.path.insert(0, str(PROJECT_ROOT))

from ml.predict import WellnessPredictor

It then offers four thin functions around a module-level singleton:

  • load_predictor() — creates the WellnessPredictor once and reuses it.
  • is_model_loaded() — used by /health.
  • predict(request) — converts the Pydantic request with request.model_dump() into a plain dict and calls the ML predictor.
  • get_metadata() — returns the loaded metadata dict for /model-info.

4.4 main.py — the FastAPI application

Startup (lifespan)

On app start, predictor.load_predictor() tries to load the artifacts. If it fails, the exception is logged but the app still starts — so /health can report model_loaded: false instead of the server refusing to boot.

CORS

CORSMiddleware allows the two local frontend origins, credentials, all methods and all headers — that is what lets the browser on port 5173 call the API on port 8000.

Endpoints

Method & pathHandlerBehaviour
GET /health health() Returns {status:"ok", model_loaded: bool}. Readiness probe.
GET /model-info model_info() Returns model metadata (name, date, features, test metrics, target-construction text). If artifacts are missing → 503 with "Run python -m ml.train".
POST /predict predict(request) Validates the body, calls the predictor, returns {prediction, score, confidence, top_factors}.

Error handling on /predict

  • 422 — Pydantic rejects missing fields, out-of-range numbers, or unknown categories, with a field-level error list. The model is never called.
  • 503 — FileNotFoundError: artifacts not present (train first).
  • 500 — any other exception: logged server-side, and the client only gets a generic "Prediction failed due to an internal error." No stack traces leak to the client.

4.5 Full request lifecycle — what happens when someone submits the form

React form ──POST /predict──► main.py :: predict(request) │ ├─ Pydantic validates 10 fields (ranges, enums) │ └─ invalid → 422, stop │ ├─ predictor.predict(request) │ └─ request.model_dump() → plain dict │ ▼ ml/predict.py :: WellnessPredictor.predict(record) ├─ dict → one-row DataFrame ├─ derive leisure_screen_ratio ├─ order columns from feature_info.json ├─ preprocessor.transform (scale + one-hot → 19 cols) ├─ model.predict → "Low" | "Moderate" | "High" ├─ model.predict_proba → confidence (e.g. 0.56) ├─ bin_edges lookup → score (e.g. 3.3) └─ top_factors (top 5) from feature_info.json │ ▼ {"prediction":"Low","score":3.3,"confidence":0.56, "top_factors":[ ... ]} │ ▼ PredictionResponse model → JSON to the browser
Every response field traces back to a file in artifacts/: prediction and confidence come from model.pkl; score from target_bin_edges in feature_info.json; top_factors from top_factors in feature_info.json; /model-info from model_metadata.json. Nothing is hard-coded in the backend.

4.6 Where is the model "visible"?

Three places, depending on what you mean by visible:

  1. As a serialized object: artifacts/model.pkl — the actual trained Logistic Regression, plus artifacts/preprocessor.pkl for the scaler/encoder. This is the model.
  2. As declared output: artifacts/model_metadata.json says "model_name": "LogisticRegression", and artifacts/metrics.json says "selected_model": "LogisticRegression" — so you can confirm which model won without unpickling anything.
  3. At runtime: every response to /predict is produced by that pickled model — ml/predict.py never invents a result.

A note on what this is: ScreenWise is an educational AI/ML project. It predicts wellness patterns learned from a fixed 400-row dataset. It is not a medical or psychological diagnostic tool, and its ~60% test accuracy reflects the size and noise of the data, not clinical validity. Feature importance values are correlations in this sample, not causal claims.
